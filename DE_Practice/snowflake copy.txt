

how to create copy data from adf to snowflake

There are several ways to copy data from Azure Data Factory (ADF) to Snowflake. The most common approach is to use an ADF Copy Activity with Snowflake as the sink.

Method 1: Use ADF Copy Activity (Recommended)
Step 1: Create Linked Services
Create a linked service for your source (for example, Azure Blob Storage, SQL Server, Azure SQL Database, ADLS Gen2, etc.).

Create another linked service for Snowflake with the following details:

Snowflake account URL

Warehouse

Database

Schema

Username and password (or Key Pair authentication if configured)

Role (optional)

Example:

Account: xy12345.us-east-1
Warehouse: COMPUTE_WH
Database: SALES_DB
Schema: PUBLIC
Role: SYSADMIN
Step 2: Create Datasets
Source dataset (CSV, SQL table, Parquet, etc.)

Snowflake dataset (target table)

Step 3: Add Copy Activity
In your pipeline:

Source → Copy Activity → Snowflake Sink
Configure:

Source

Select source dataset

Write query or choose table

Sink

Select Snowflake dataset

Choose target table

Enable Auto Create Table if desired (if supported by your ADF version)

Step 4: Configure Mapping
Import schemas and map columns.

Example:

Source	Snowflake
id	ID
name	NAME
salary	SALARY
Step 5: Run Pipeline
ADF performs the following:

Read source
      ↓
Stage files (temporary)
      ↓
Execute Snowflake COPY INTO
      ↓
Load data into table
This staging and COPY INTO process is one reason ADF provides efficient bulk loading into Snowflake.

Method 2: Load Files into Azure Storage, Then Snowflake
Architecture:

SQL Server
     ↓
ADF
     ↓
Azure Data Lake / Blob Storage
     ↓
Snowflake Stage
     ↓
COPY INTO table
Example Snowflake SQL:

COPY INTO EMPLOYEE
FROM @MY_STAGE/employee.csv
FILE_FORMAT = (
    TYPE = CSV
    SKIP_HEADER = 1
);
Method 3: Use Snowflake Connector in ADF
ADF has a native Snowflake connector.

Pipeline example:

Azure SQL
     ↓
ADF Copy Activity
     ↓
Snowflake
No custom code is required.

Performance Tips
Use Parquet instead of CSV when possible for better performance.

Increase the Snowflake warehouse size for larger loads.

Partition large datasets to enable parallel processing.

Use bulk loads instead of row-by-row inserts.

Enable parallel copy in ADF where appropriate.

Incremental Load Pattern
For incremental loads:

Store the last successful load timestamp.

Query only new or updated rows from the source.

Example source query:

SELECT *
FROM Orders
WHERE ModifiedDate > @LastLoadTime;
Then load only those records into Snowflake.

Common Issues
Authentication failures: Verify the Snowflake account identifier, username/password or key pair, warehouse, and role.

Permission errors: Ensure the Snowflake role has USAGE on the warehouse, database, and schema, and INSERT (or appropriate) privileges on the target table.

Data type mismatches: Review ADF column mappings and ensure source and target data types are compatible.

Performance bottlenecks: Use larger warehouses, parallelism, and columnar formats like Parquet for large datasets.

A Dynamic Table in Snowflake automatically keeps its data up to date by running a query on a schedule that Snowflake manages. It's useful for incremental transformations, aggregations, and ETL pipelines.

Syntax
CREATE OR REPLACE DYNAMIC TABLE <table_name>
TARGET_LAG = '<time>'
WAREHOUSE = <warehouse_name>
AS
SELECT ...
Parameters
TARGET_LAG: Maximum acceptable data freshness (for example, '1 minute', '5 minutes', '1 hour', or 'DOWNSTREAM').

WAREHOUSE: The virtual warehouse Snowflake uses to refresh the table.

AS SELECT: The query that defines the table.

Example 1: Dynamic Table from a Base Table
Suppose you have a table:

CREATE TABLE students (
    id INT,
    name STRING,
    marks NUMBER
);
Create a dynamic table:

CREATE OR REPLACE DYNAMIC TABLE dt_students
TARGET_LAG = '5 minutes'
WAREHOUSE = COMPUTE_WH
AS
SELECT
    id,
    name,
    marks
FROM students;
Snowflake refreshes dt_students automatically so it stays within five minutes of the source data.

Example 2: Filter Data
CREATE OR REPLACE DYNAMIC TABLE dt_pass_students
TARGET_LAG = '10 minutes'
WAREHOUSE = COMPUTE_WH
AS
SELECT *
FROM students
WHERE marks >= 35;
Example 3: Aggregate Data
CREATE OR REPLACE DYNAMIC TABLE dt_department_summary
TARGET_LAG = '15 minutes'
WAREHOUSE = COMPUTE_WH
AS
SELECT
    department,
    COUNT(*) AS employee_count,
    AVG(salary) AS avg_salary
FROM employees
GROUP BY department;
Example 4: Join Tables
CREATE OR REPLACE DYNAMIC TABLE dt_orders
TARGET_LAG = '5 minutes'
WAREHOUSE = COMPUTE_WH
AS
SELECT
    o.order_id,
    o.order_date,
    c.customer_name
FROM orders o
JOIN customers c
ON o.customer_id = c.customer_id;
Example 5: Chain Dynamic Tables
CREATE OR REPLACE DYNAMIC TABLE dt_sales_summary
TARGET_LAG = 'DOWNSTREAM'
WAREHOUSE = COMPUTE_WH
AS
SELECT
    region,
    SUM(amount) AS total_sales
FROM sales
GROUP BY region;
TARGET_LAG = 'DOWNSTREAM' is useful when another dynamic table depends on this one.

Check Refresh Status
SHOW DYNAMIC TABLES;
Or:

DESCRIBE DYNAMIC TABLE dt_students;
Refresh History
SELECT *
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(
    NAME => 'DT_STUDENTS'
));
Suspend and Resume
Suspend refreshes:

ALTER DYNAMIC TABLE dt_students SUSPEND;
Resume refreshes:

ALTER DYNAMIC TABLE dt_students RESUME;
Drop a Dynamic Table
DROP DYNAMIC TABLE dt_students;
Dynamic Table vs. Stream + Task
Dynamic Table	Stream + Task
Automatically maintains query results	Requires you to build and schedule tasks
Less operational overhead	More control over processing logic
Best for transformations and derived datasets	Best for custom ETL workflows and procedural logic
Can You Create a Dynamic Table Directly from a Stage?
No. A dynamic table's query must reference supported database objects such as tables or views. It cannot directly read from an external stage like:

-- Not supported
SELECT * FROM @adf_stage;
If your data starts as CSV files in a stage, the typical workflow is:

Load the files into a Snowflake table using COPY INTO (or Snowpipe).

Create one or more dynamic tables on top of that loaded table for ongoing transformations.


downstream refresh time

TARGET_LAG = 'DOWNSTREAM' does not specify a fixed refresh time like '5 minutes' or '1 hour'.

Instead, it means:

Refresh this dynamic table only when a downstream dynamic table needs fresh data.

Example
SALES (Base Table)
      │
      ▼
DT_SALES
TARGET_LAG = DOWNSTREAM
      │
      ▼
DT_MONTHLY
TARGET_LAG = '10 minutes'
      │
      ▼
DT_REPORT
TARGET_LAG = '30 minutes'
In this example:

DT_REPORT refreshes every 30 minutes (or sooner if needed to meet its lag target).

Before DT_REPORT refreshes, Snowflake checks DT_MONTHLY.

Before DT_MONTHLY refreshes, Snowflake refreshes DT_SALES.

So DT_SALES doesn't have its own schedule. It refreshes only when one of its downstream dependencies is being refreshed.

When to Use DOWNSTREAM
Use it for intermediate transformation layers:

CREATE DYNAMIC TABLE dt_stage
TARGET_LAG = 'DOWNSTREAM'
WAREHOUSE = COMPUTE_WH
AS
SELECT * FROM raw_table;
Then create a final reporting table:

CREATE DYNAMIC TABLE dt_report
TARGET_LAG = '15 minutes'
WAREHOUSE = COMPUTE_WH
AS
SELECT *
FROM dt_stage;
In this setup:

dt_stage refreshes only when dt_report needs it.

dt_report is refreshed approximately every 15 minutes (subject to Snowflake's scheduling to satisfy the lag target).

Can You Mix DOWNSTREAM and Time-Based Lags?
Yes. This is a common pattern:

Raw Table
    │
    ▼
DT_CLEAN
TARGET_LAG = DOWNSTREAM
    │
    ▼
DT_AGG
TARGET_LAG = DOWNSTREAM
    │
    ▼
DT_REPORT
TARGET_LAG = '5 minutes'
Only DT_REPORT has a refresh target. The upstream dynamic tables refresh automatically as needed to keep DT_REPORT within its 5-minute lag.

This approach avoids unnecessary refreshes of intermediate tables while keeping the final reporting table up to date.


can we create dynamic table using stage

No. You cannot create a dynamic table directly from a stage.

For example, this is not supported:

CREATE DYNAMIC TABLE dt_students
TARGET_LAG = '5 minutes'
WAREHOUSE = COMPUTE_WH
AS
SELECT *
FROM @adf_stage;
or

CREATE DYNAMIC TABLE dt_students
TARGET_LAG = '5 minutes'
WAREHOUSE = COMPUTE_WH
AS
SELECT *
FROM @adf_stage/input
(FILE_FORMAT => csv_ff);
This is because a dynamic table's query must reference supported database objects such as:

Tables

Views

Other dynamic tables

It cannot directly query files from a stage.

Recommended Architecture
CSV Files
      │
      ▼
External Stage
      │
      ▼
COPY INTO (or Snowpipe)
      │
      ▼
Raw Table
      │
      ▼
Dynamic Table
      │
      ▼
Reporting Dynamic Tables
Example
Load data into a table:

COPY INTO raw_students
FROM @adf_stage/input
FILE_FORMAT = (FORMAT_NAME = csv_ff);
Create a dynamic table on top of it:

CREATE OR REPLACE DYNAMIC TABLE dt_students
TARGET_LAG = '5 minutes'
WAREHOUSE = COMPUTE_WH
AS
SELECT
    id,
    name,
    age
FROM raw_students;
If You Need to Query Files Without Loading
Instead of a dynamic table, you can use:

An external table (best suited for formats like Parquet, JSON, Avro, and ORC).

A view over an external table.

For CSV files, the recommended approach is still to load them into a Snowflake table using COPY INTO or Snowpipe, then build dynamic tables on that loaded data.

If you're preparing for a Snowflake interview or certification, remember this rule:

❌ Stage → Dynamic Table: Not supported.

✅ Stage → COPY INTO/Snowpipe → Table → Dynamic Table: Supported and recommended.
